System Overview & Architecture

How all the pieces fit together

CareerPath Africa is a multi-role education platform built as a monorepo. It consists of two main applications that communicate over a REST API:

Portal (Frontend)
Next.js 15
App Router, Tailwind CSS v4. Serves all role-specific portals from a single app using middleware-based route protection.
API (Backend)
NestJS + Prisma
REST API with JWT auth, role guards, PostgreSQL via Prisma ORM. Handles all business logic, payments, file storage.
Database
PostgreSQL
Single database for all data. Managed via Prisma schema with prisma db push.
File Storage
Cloudflare R2
All uploaded files (assignments, course assets, covers). Uploaded via POST /files/upload.
Live Video
Daily.co
Browser-based live class rooms. Teachers create rooms; students join via iframe embed.
Email
Mail Service
Transactional emails for teacher approvals, payment confirmations, certificate delivery.

High-Level Architecture

🌐 Browser Student / Teacher / Admin
⚡ Next.js Portal Route protection via middleware
🔌 NestJS API JWT guards + role checks
🗄️ PostgreSQL Via Prisma ORM
Important The portal's middleware provides a first layer of route protection (role-based redirects). Real security is enforced by the NestJS API on every request — the API checks JWT validity and role on every endpoint independently.

User Roles & Access Control

Six distinct roles, each with their own portal section

Role Portal Path Description Assigned By
Student /student/* Buys packages or individual courses. Accesses content, live classes, assignments, certificates. Self-registration
Teacher /teacher/* Applies to teach. Builds courses, manages cohorts, runs live classes, grades assignments, earns commissions. Admin approval after application
Admin /admin/* Full platform control. Manages users, courses, packages, cohorts, payouts, reports. Admin sets role via User Management
Country Rep /country-rep/* Regional ambassador. Sees analytics and commission earnings for their country's sales. Admin sets role
Subject Reviewer /reviewer/* Domain expert. Reviews and approves/rejects courses submitted by teachers. Earns per review. Admin sets role + assigns payout currency
Public /courses, /packages Unauthenticated visitor. Can browse the public course catalogue and package listings. No account needed
Route Protection Rule If a user with role TEACHER tries to access /student/*, the portal middleware redirects them to /teacher/dashboard. The same applies for all role-to-path mismatches.
03

Authentication

JWT-based, cookie-stored, role-aware

How Login Works

  1. User submits credentials POST /auth/login — email + password. Returns a signed JWT.
  2. JWT stored in cookie Cookie name: cpa_token. HttpOnly in production. Contains: sub (user ID), role, exp.
  3. Middleware reads cookie on every request Decodes JWT, checks expiry, enforces role-to-path rules. Expired tokens are deleted and user is sent to /login.
  4. API validates JWT on every endpoint JwtAuthGuard + RolesGuard on all protected routes. The API never trusts the frontend alone.

Registration Flows

FlowRouteNotes
Student registrationPOST /auth/registerImmediately gets STUDENT role. Can purchase right away.
Teacher applicationPOST /auth/apply-teacherCreates account with TEACHER role + PENDING status. Cannot access teacher portal until approved by admin.
Promote existing userPATCH /portals/admin/users/:id/roleAdmin-only. Used to make someone a Country Rep, Reviewer, or Admin.

Key Auth Endpoints

POST /auth/login POST /auth/register POST /auth/apply-teacher GET /auth/me POST /auth/logout

Teacher Approval Required A teacher who registers cannot access the teacher portal until an admin approves their application at Admin → Teachers → Pending.

Student Portal

Everything a student sees and does after enrolling

4.1 Dashboard

The dashboard is the student's home screen. It shows a real-time summary pulled from the API:

  • Active package count and names
  • Number of individually purchased courses
  • Upcoming live classes (next 3)
  • Certificate count
  • Wallet balance (if applicable)

If the student has no packages or course purchases, the dashboard shows empty states with CTAs to browse packages and courses.

4.2 Courses & Learning

Catalogue (/student/catalogue)

Shows all published courses. Access indicators show whether the student can enter a course (green tick = has access, lock = need to purchase). Courses can be filtered by programme, subject, and source.

For individually-sold courses, a Buy this course button appears alongside the package option.

Course Player (/student/learn/[courseId])

The portal first verifies access before loading the player:

  1. Check active packagesDoes the student have an active package that includes this course?
  2. Check direct purchasesDoes the student have a valid individual CoursePurchase for this course?
  3. Grant or deny accessIf neither — show "Access required" screen with buy options. If yes — load the player.

For Native courses: modules and lessons load in the portal's built-in player with progress tracking, video, text content, and resume functionality.

For WordPress courses: an "Open course" button redirects the student to the LearnDash page on the WordPress site.

Expiry Warning If the student's package or direct purchase expires within 7 days, a yellow warning banner appears in the player with a "Renew now" link.

4.3 Assignments

Assignments are created by teachers and attached to cohorts. Students see all assignments across all their cohorts at /student/assignments.

StatusMeaning
PendingAssignment is active; student has not submitted yet
SubmittedStudent has uploaded a file; awaiting teacher grading
GradedTeacher has reviewed and assigned a grade (0–100)

Submission uploads a file to Cloudflare R2 via POST /files/upload?folder=submissions and then calls POST /education/assignments/:id/submit.

4.4 Live Classes

Students see their upcoming live classes at /student/live. When a class is LIVE, a Join now button appears. The live class page embeds a Daily.co iframe in participant mode.

Live class statuses: SCHEDULED → LIVE → COMPLETED.

4.5 Cohort & Exam Countdown

Students assigned to a cohort see their group at /student/cohort. This page shows:

  • Cohort name, teacher info, student count, session count
  • Next scheduled or live class with a "Join now" button
  • Full list of all sessions with statuses
  • Exam countdown banner (for certification programmes like ACCA, CFA, IELTS)
  • Book 1-on-1 mentorship with the cohort teacher

The exam countdown changes colour based on urgency:

Days until examBanner colour
More than 14 daysBlue (calm)
8–14 daysAmber (warning)
1–7 daysDeep amber / orange (urgent)
0 or pastGrey (passed)

4.6 Mentorship

Students can book 1-on-1 sessions with teachers who have open availability slots. The mentorship page (/student/mentorship) reads cohort data to surface the student's own teacher first, making booking quick.

4.7 Certificates

Certificates are issued when a student completes all lessons in a course. The certificates page (/student/certificates) lists all earned certificates with:

  • Certificate download link
  • LinkedIn "Add to profile" share button
  • Public verification URL (anyone can verify authenticity)

Teacher Portal

Course creation, cohort management, grading, live classes, and earnings

Approval Required A teacher account must be approved by an admin before access to the teacher portal is granted. Until approved, login redirects to a pending screen.

5.1 Dashboard

The teacher dashboard shows at a glance:

  • Grading queue — submissions waiting for a grade
  • Upcoming live classes (scheduled)
  • Quick links to cohorts and wallet

5.2 Course Builder

Teachers create native courses at /teacher/courses/[courseId]/builder. The builder supports:

FeatureDetails
ModulesDrag-and-drop reordering. Each module has a title and contains lessons.
Lesson typesVIDEO (upload or URL), TEXT (rich text editor), QUIZ (question-based)
Rich text editorTiptap-based: bold, italic, underline, headings, lists, blockquote, code, undo/redo
File attachmentsPDFs/DOCX attachable to lessons
Submit for reviewWhen complete, teacher clicks "Submit for review" — status moves to PENDING_REVIEW

Course Publication Flow

📝DRAFTTeacher building
📤PENDING_REVIEWSubmitted by teacher
👁️ReviewAdmin or Reviewer
✅PUBLISHEDLive to students

5.3 Assignment Grading

At /teacher/assignments, teachers see all submissions from students in their cohorts. Each submission shows the uploaded file, submission date, and current status.

Grading: teacher clicks a submission, enters a grade (0–100) and optional feedback, then saves. The API call is PATCH /education/submissions/:id/grade with { grade, feedback }.

5.4 Live Class Management

At /teacher/live, teachers can:

  • Schedule a new live class for one of their cohorts (title, date/time)
  • See all upcoming and past sessions
  • Start a class — changes status to LIVE, creates a Daily.co room, issues a student join link
  • End a class — marks it COMPLETED

The live class host view (/teacher/live/[classId]) embeds the Daily.co room with host controls (mute, camera, kick participants, end meeting).

5.5 Wallet & Earnings

Every teacher has a wallet. When a student purchases a package or course that includes a teacher's course, the teacher automatically receives a commission credit to their wallet.

At /teacher/wallet, teachers see:

  • Current wallet balance and currency
  • Transaction history (each purchase that generated a commission)
  • Payout statements (amounts paid out)

Payouts are initiated by the admin (see Section 16).

5.6 Mentorship Slots

Teachers manage their availability at /teacher/mentorship. They can add time slots (date, start time, duration) and see which slots have been booked by students.

Admin Portal

Full platform control — the central command centre

6.1 User Management (/admin/users)

Admins can search and list all users. For any user, the admin can:

  • Change their role (Student, Teacher, Country Rep, Subject Reviewer, Admin)
  • Assign a payout currency when promoting to Subject Reviewer
  • View their email, current role, and approval status

6.2 Teacher Approvals (/admin/teachers)

New teacher applications arrive here with PENDING status. The admin can:

  • Review the teacher's application (bio, qualifications)
  • Approve — teacher gains portal access immediately
  • Reject — optionally supply a rejection reason sent by email

6.3 Cohort Management (/admin/cohorts)

Cohorts are learning groups that connect students to a teacher. Admins create and manage cohorts:

FieldPurpose
Namee.g. "ACCA F3 — March 2025 Cohort"
TeacherAssigned teacher (must be an approved teacher)
Sitting Labele.g. "March 2025 Sitting" — shown on student exam countdown
Exam DateTriggers countdown timer visible to teacher and students
Start DateWhen tuition begins
StudentsAdded by email address. Can be removed at any time.

From a cohort's detail panel, the admin can add students by email, remove students, and edit exam fields (sitting label, exam date, start date) inline.

Exam Countdown Setting an Exam Date on a cohort activates a visual countdown for both the assigned teacher and all students in the cohort. The countdown turns amber at 14 days and urgent at 7 days.

6.4 Course Management (/admin/courses)

All platform courses (native and WordPress-synced) are visible here. Per course, admins can:

  • View curriculum (modules and lessons)
  • Edit tags — assign Programme, Subject, Level, Teacher
  • Set individual pricing — price amount, currency, enable "sold individually" toggle
  • Publish (moves PENDING_REVIEW → PUBLISHED)
  • Archive (hides from students)
  • Sync WordPress courses (pulls from WP/LearnDash via WP Sync button)

Setting Individual Course Pricing

Click the Pricing button on any course detail page. Set:

  • Price amount — integer (e.g. 5000 for GHS 50.00)
  • Currency — 3-letter code (GHS, USD, XAF, etc.)
  • Sold individually — toggle on to allow standalone purchase

6.5 Packages (/admin/packages)

Packages bundle multiple courses and are the primary purchase unit. Admins create packages with:

  • Name and description
  • Course IDs to include
  • Price amount and currency (GHS / USD / XAF routes to Paystack or Tranzak)
  • Validity period (days) — null means lifetime access
  • Category tags — used for filtering on the packages page

6.6 Coupons (/admin/coupons)

Admins create discount codes applied at package checkout:

  • Code (e.g. "SAVE20")
  • Discount type: flat amount or percentage
  • Expiry date and max uses

6.7 Reports (/admin/reports)

Date-range analytics report with CSV export. Covers purchases, revenue by package, and enrolment trends. Uses a date picker for custom ranges.

6.8 Payouts (/admin/payouts)

The admin reviews pending wallet balances for teachers and subject reviewers, then records payouts manually (bank transfer outside the system) and marks them as paid in the portal. This creates a PayoutStatement and deducts the wallet balance.

07

Country Rep Portal

Regional ambassador analytics and commission tracking

Country Representatives are assigned to a specific country. When a student from their country purchases a package or course, the country rep earns a commission that is credited to their wallet.

The country rep dashboard (/country-rep/dashboard) shows:

  • Recharts analytics: sales over time, revenue by package for their country
  • Commission calculator — simulates earnings for different price points
  • Wallet balance and transaction history

Country reps are promoted from student accounts by admins via Admin → Users → Change Role. They do not register separately.

08

Subject Reviewer Portal

Domain experts who validate course content quality

Subject Reviewers are assigned courses to review by the admin via /admin/reviews. Once assigned, the course appears in the reviewer's queue at /reviewer/dashboard.

For each course in the queue, the reviewer can:

  • Browse the full curriculum (modules and lessons)
  • Approve — moves course to PUBLISHED status
  • Reject — supply a reason; course returns to DRAFT for the teacher to fix

Reviewers earn a flat fee per review, credited to their wallet. Admins set the payout currency when assigning the reviewer role.

Payments & Checkout

Paystack, Tranzak, webhooks, and fulfillment logic

9.1 Payment Gateways

The platform supports two payment gateways, routed by currency:

GatewayCurrenciesUse case
PaystackGHS, NGN, ZAR, USDGhana, Nigeria, South Africa and USD payments
TranzakXAF, XOFFrancophone Africa (Cameroon, Côte d'Ivoire, etc.)

The PaymentsService automatically picks the correct gateway based on the package or course currency. No manual configuration is needed per purchase.

9.2 Package Checkout Flow

  1. Student clicks "Enroll" on a packagePortal calls POST /payments/create-checkout/:packageId. Optional coupon code included.
  2. API creates a checkout sessionCalls gateway (Paystack or Tranzak) to generate a hosted payment URL. Returns { url } to the portal.
  3. Portal redirects student to payment pageStudent completes card/mobile money payment on the gateway's hosted page.
  4. Gateway sends webhook to APIPOST /payments/webhook/paystack or /payments/webhook/tranzak. API verifies signature.
  5. API fulfills the purchase (idempotent)Creates PackagePurchase, enrolls student in all package courses, credits teacher and country rep wallets.
  6. Student redirected to success page/packages/success — waits 1.5 seconds, calls /auth/me to refresh session, redirects to dashboard.

9.3 Individual Course Checkout Flow

Students can buy specific native courses without a package, if the admin has enabled isSoldIndividually on the course.

  1. Student clicks "Buy now" on /courses or /student/catalogueNavigates to /student/courses/[courseId]/checkout.
  2. Checkout page confirms course details and priceShows what's included (lesson access, certificates) vs what requires a package (live classes, mentorship).
  3. Student clicks "Pay"Portal calls POST /payments/create-course-checkout/:courseId.
  4. Same gateway/webhook flow as packagesWebhook identifies courseId in metadata and routes to fulfillCoursePurchase.
  5. Creates CoursePurchase recordStudent redirected to /student/courses/success?courseId=... then to the learn page.

9.4 Webhook Fulfillment

All fulfillment logic runs inside the webhook handler, making it idempotent — if a webhook fires twice (network retry), the second call is ignored.

Idempotency Before creating a PackagePurchase or CoursePurchase, the API checks if one already exists for this student + package/course combination. If it does, the webhook handler returns early without double-crediting.

9.5 Coupons

A coupon code entered at checkout reduces the payment amount before the gateway session is created. The API validates the coupon (exists, not expired, uses remaining) and applies the discount. The coupon use count increments on successful payment only.

Discount typeExample
Flat amountCoupon "OFF50" reduces price by GHS 50
PercentageCoupon "SAVE20" reduces price by 20%

Live Classes (Daily.co)

Real-time video sessions between teachers and cohort students

Live classes are tied to cohorts — only students in the cohort can join. They are powered by Daily.co, which provides browser-based video rooms with no app install required.

Teacher Flow

  1. Schedule a classTeacher selects cohort, enters title and date/time. API creates a LiveClass record with status SCHEDULED.
  2. Start the classTeacher clicks "Start" — API calls PATCH /live/classes/:id/start. This creates a Daily.co room and changes status to LIVE.
  3. Host the sessionTeacher's view embeds the Daily.co room with host controls (mute all, screenshare, end meeting).
  4. End the classTeacher clicks "End" — API calls PATCH /live/classes/:id/end. Status moves to COMPLETED. Daily.co room is closed.

Student Flow

When a class status changes to LIVE, a Join now button appears on the student's cohort page and live classes page. Clicking it opens the Daily.co room in participant mode (no host controls).

StatusStudent sees
SCHEDULEDDate/time, "Upcoming" badge
LIVEBlue pulsing indicator, "Join now" button
COMPLETED"Done" badge, session is over

Two content delivery methods, unified payment

Key rule All payments go through the portal regardless of course type. WordPress is content-only — it never handles money. When a student pays for a package containing a WP course, the portal redirects them to the WP URL after confirming their active package.

WP Sync Process

  1. Admin clicks "Sync WP Courses"At /admin/courses. Calls POST /platform-courses/wp-sync.
  2. API fetches all published courses from WPCalls the WordPress REST API. Reads title, description, and course URL.
  3. Upserts into PlatformCourse tableNew courses created. Existing ones updated (title, URL). Nothing deleted automatically.
  4. Admin tags coursesUse the "Edit tags" button to assign Programme, Subject, Level to imported WP courses for searchability.

Public Course Catalogue

Discovery page for unauthenticated visitors

The public course catalogue at /courses is accessible to anyone — no account required. It serves as a marketing storefront for the platform.

What it shows

  • All published courses (both NATIVE and WORDPRESS)
  • Programme, subject, and level tags per course
  • Price and "Buy now" CTA for individually-sold courses
  • "Package only" badge with "View packages" link for courses not sold individually
  • Module count and enrollment count per course

Filter options

  • Search by course title, programme name, or subject
  • Filter: All / Buy individually / Package only

Visitor vs Logged-in behaviour

Visitor typeBuy button goes to
Not logged in/login — then forwarded to checkout
Logged-in student/student/courses/[id]/checkout directly

Powered by

The page calls GET /catalogue/courses — a public API endpoint with no authentication required. It returns only PUBLISHED courses and includes pricing fields.

Linking from WordPress To surface this catalogue for people browsing the WP site, add a navigation menu item in WordPress admin (Appearance → Menus) pointing to https://yourportal.com/courses. No code changes needed on WP.

WordPress Integration

How WP and the portal coexist

Responsibilities split

FunctionWordPressPortal
Course content (videos, lessons)✅ Hosts it—
User accounts—✅ Single source of truth
Payments❌ Never✅ Always
Access control—✅ Portal grants/checks
Course metadata (title, tags)Source✅ Synced copy
Analytics & reports—✅
Certificates—✅

One-way sync

The sync is WP → Portal only. Changes on WP (title, URL) get pulled in when admin runs WP Sync. The portal never writes back to WP.

Payment does NOT touch WP

When a student buys a package containing a WP course:

  1. Payment processed on portalPaystack/Tranzak webhook → PackagePurchase created.
  2. Student visits course in portalPortal checks PackagePurchase — access confirmed.
  3. Portal shows redirect button"Open course" → wpCourseUrl opens in new tab.
  4. Student watches content on WPWordPress/LearnDash serves the video. Student must be enrolled in the WP course on the WP side (manual or via WP API if you choose to automate).
WP Enrollment Gap The portal does not automatically enroll students into LearnDash on WordPress after payment. This is a deliberate simplification — if you want seamless access on WP, you'd need to call the WP REST API from the portal's webhook handler to create a LearnDash enrollment. This is an optional future enhancement.

Certificates

Issued on course completion, shareable to LinkedIn

A certificate is generated automatically when a student completes all lessons in a native course (100% progress). Certificates have:

  • Unique certificate ID for public verification
  • Student name, course title, completion date
  • Download link (PDF or image)
  • LinkedIn "Add to profile" button (pre-fills LinkedIn certificate form)
  • Public verification URL — anyone can confirm authenticity without logging in
Note on WordPress courses Certificates for WP courses are managed by LearnDash on WordPress. The portal only issues certificates for native courses where it can track lesson completions.

Wallets & Payouts

Earnings, commissions, and how money flows to contributors

Who has a wallet

RoleEarns from
TeacherCommission when a student buys a package or course containing their content
Country RepCommission on purchases made by students from their assigned country
Subject ReviewerFlat fee per course review completed

Payout flow

  1. Earnings accumulateEvery successful purchase triggers automatic wallet credits for the relevant teacher and country rep.
  2. Admin reviews balancesAt /admin/payouts — sees all wallets with positive balances.
  3. Admin pays out (off-platform)Bank transfer, mobile money, or other method outside the portal.
  4. Admin records the payoutMarks as paid in the portal. Creates a PayoutStatement, deducts wallet balance to zero.
  5. Teacher / Rep sees updated balanceWallet balance resets, payout appears in statements history.
Currency Each wallet has a single currency, set when the role is assigned. All credits for that user are in that currency. If a user earns in multiple currencies (e.g. a teacher with students from Ghana and Cameroon), this is a future enhancement — current design is one wallet per user.
